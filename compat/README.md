# Legacy compatibility checks

`compat/legacy` is an independent consumer module. Its generated files are
frozen output of gogo/protobuf v1.3.2 (b03c65e), generated with protoc 36.2.
Do not regenerate these fixtures while updating the generator or runtime.

Run `sh compat/check.sh` with protoc 3.21.8 or 36.2 on PATH. It checks two independent
paths: frozen generated code against the candidate runtime, and unchanged
schemas regenerated by the candidate generator. The root suite also covers
proto2 defaults, extensions, custom types, WKT and the existing plugin matrix.

The version helper accepts both historical three-component versions and modern
two-component versions. CI checks both compiler families.

The v1.3.2 golden generator tests require protoc-min-version and protoc-gen-gogo
on PATH; the script builds them before running the suite. The consumer uses
replace to keep original imports and avoid linking two runtime identities.
Historical integration tests run in a disposable GOPATH-shaped copy because
some resolve proto imports through relative paths. No source tests are skipped.
The historical `testdata/multi` goldens are ignored by the original repository.
`compat/golden/multi` freezes them using the original v1.3.2 generator; the
script copies those references into the disposable suite before testing.

`sh compat/check-optional.sh` checks optional through the production gogo and
gogofast generators. The fixtures cover every scalar, explicit empty bytes, real and synthetic
oneofs, JSON/text, Merge/Clone/Equal, and UTF-8 in reflection and fast paths.

`sh compat/check-entrypoints.sh` compiles and runs the presence tests separately
for gogo, gogofast, gogofaster, gogoslick and gogotypes, and compiles auxiliary
GoString output. It verifies diagnostics for unsupported extensions and gofast's
alternate runtime, plus the compile-time rejection of new feature code by the
unmodified v1.3.2 runtime. Custom auxiliary plugins must explicitly implement
SupportsProto3Optional before GeneratePlugin advertises that capability.

Proto3 optional currently requires the gogo runtime and default pointer-based
scalar representations. nullable=false, customtype/casttype, embedded fields,
standard-type mappings, face and union combinations are rejected for optional
fields. Existing proto2/proto3 configurations keep their historical behavior.
Editions support is not yet advertised.

The Editions foundation adds protocol declarations from protobuf 36.2 while
retaining historical fields and defaults that newer upstream schemas removed.
`merge-protocol.py` merges only additions and is idempotent; it does not replace
the legacy schema wholesale. Bootstrap protocol code with the frozen v1.3.2
plugins using `regenerate-protocol.sh`. `regenerate-features.sh` uses protoc 36.2
to compile canonical feature defaults into a Go 1.15-compatible byte table.

`internal/semantics` resolves core defaults, allowed targets, fixed features and
lexical inheritance without rewriting raw descriptors. Extensions inherit their
declaration scope; structural presence is handled separately. `internal/fieldmeta`
has no generator, descriptor or runtime dependencies. These modules do not yet
enable Editions output: production generators continue to reject Editions until
the corresponding encoding and runtime paths are implemented and validated.

The original randomized TestStdTypesGoString can intermittently emit invalid Go
expressions for nil standard-type pointers. This also reproduces on unmodified
v1.3.2; the compatibility scripts do not skip or suppress that test.

Generated snapshots compare Go syntax and decompressed descriptor bytes. This
ignores only comments, formatting and gzip representation, which vary between
Go toolchains. Field tags, declarations, function bodies and descriptor data
must match; frozen consumer files are still compiled without modification.

The protocol merge CLI formats its output with clang-format using Google style
and preserving comment text (`ReflowComments: false`). Set `CLANG_FORMAT` to
select the formatter binary; the checked-in protocol files use clang-format
21.1.4. Formatting does not change descriptor fields or defaults.
